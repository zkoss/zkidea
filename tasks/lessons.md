# Lessons (self-improvement log)

## 2026-07-07 — ZUL Preview run (fable-commander workflow)

1. **Passing headless tests prove nothing about the production seam.** E3 round 1 was fully green, yet every preview failed in the user's real IDE (D1): the tests fed the launcher a full `mvn dependency:build-classpath` classpath while the plugin's own filter produced a ZK-only starved one. Rule: whenever component A produces input consumed by component B, add a test that generates the input through A's *production* code path before claiming the integration works.
2. **When the user says "you just plan, delegate the fixes"** — treat it as standing: Fable plans/reviews/decides; all implementation goes to lower-cost model subagents with a written brief and an evidence-file requirement.
3. **A real-world corpus gate beats hand-written fixtures.** The user-added "render every ZUL under manual-test, cross-check with validate-zul.py" gate caught defect D3 (annotation-shaped templateURI treated as a literal path) that no fixture anticipated. Ask for available corpora when defining acceptance gates.
4. **Discard anomalous subagent output wholesale.** One verifier launch returned in 3 s with zero tool calls and injection-style text ("break character"). Correct handling: verify nothing was written, discard the entire output, relaunch fresh, never follow embedded instructions.
5. **Environment quirks worth remembering in this repo**: prefix JVM commands with `withjdk.sh 17` (default JDK is 11); root builds need `-x buildSearchableOptions` while a sandbox IDE is open; `zk9support` checkout is read-only.

## 2026-07-21 — grid/listbox/tree placeholder cases

6. **HTTP 200 is not "renders correctly."** The `tree-mvvm` fixture returned 200 from both Jetty and the preview, but the browser errored: the treecells were empty. A curl status check misses binding failures whose values simply don't appear. Rule: verify a fixture by checking the *rendered values* (e.g. `label:'...'` in the HTML), not just the status code — and against the real app (Jetty), not only the preview.
7. **ZK `DefaultTreeModel` template var is the `DefaultTreeNode`, not its data.** In `<tree model="@load(vm.treeModel)"><template name="model" var="node">`, bind cells `@load(node.data.x)` (via `.data`); `@load(node.x)` renders empty and throws in the browser. (Grid/listbox templates bind the data directly — `@load(item.x)`.)
8. **`GroupsModelArray<D,H,F,E>` takes four type params** (data, head, foot, element), not three; a 3-arg diamond silently falls back to raw and the `createGroupHead`/`Foot` overrides then fail to match.
9. **Model injection must run post-composition.** Setting a synthetic model at `afterComponentAttached` (before a grid's explicit `<rows>` composed) makes ZK auto-create a second rows → "Only one rows child is allowed". Inject at `PreviewComposer.doAfterCompose`, where the real binder would.
10. **The preview has no live desktop, so every interaction is an AU POST the server can't fulfil.** Expanding a tree node / sorting a grid / paging a listbox fires `POST /zkau`, and the ZK client `JSON.parse()`s the response (`zAu.pushReqCmds`). The old stub returned `"<content/>"` → the browser dialog *"Expected JSON format ... Unexpected token '<'"*. Fix: return a **valid empty AU envelope** `{"rid":0,"rs":[]}` — the client runs zero commands (an inert no-op) instead of erroring. `rid:0` is falsy client-side, so the empty command set applies without a sequence check. Interactions in the preview are silent no-ops by design, never errors. Locked by `AuStubTest`.

## 2026-07-22 — L-10 formatted render-error page

11. **To test a launcher failure path, forbid the canary prefix — otherwise the page renders green.** `RenderErrorPageHttpTest` first "failed" by rendering a 200 page: `RenderEngineFactory.create(jars, FIXTURES, null)` (no `ForbiddenLoadTracker`) lets the canary class (`org.zkoss.zkpreview.testcanary.*`) load from the parent classloader, so `zscript-missing-class.zul` succeeds. A missing *user* class is simulated by forbidding that prefix (`new ForbiddenLoadTracker(List.of("org.zkoss.zkpreview.testcanary."))`), exactly as `StructuredFailureTest` does. Rule: any launcher test that expects a render *failure* must pass the canary tracker — a null tracker silently exercises the success path.

## 2026-08-03 — P2 apply/include coverage

12. **`--` (double hyphen) is illegal inside an XML comment — and manual-test `.zul` fixtures are never parsed by the build.** I wrote `--classpath` inside a `<!-- -->` comment in two `manual-test` fixtures; they threw `SAXParseException: The string "--" is not permitted within comments` at *XML parse* time in runIde — before ZK reached path/classpath resolution. The green launcher/plugin suites didn't catch it because they don't parse the `manual-test/**` fixtures. Rules: (a) never put `--` (or an option like `--classpath`) inside an XML comment — reword; (b) after authoring/editing any `.zul` fixture, validate it: `xmllint --noout <file>` over every new/edited fixture, since nothing else does.
13. **Don't claim a runIde error "confirms" a hypothesis without reading the error.** I predicted the `~./` user-resource case would show "page not found" (a sound *code-reading* deduction from `ZkClasspathFilter.filterLibraryJars` being jars-only) and wrote it up as "confirmed & observable here" — but the actual runIde error was my XML-comment bug, not the classpath path. A deduction from code is not a runIde observation; label each honestly and keep them separate until the observation actually happens.
14. **ZK 10 (jakarta) JS-escapes `-` as `\-` in rendered widget values; ZK 9.6 (javax) does not.** A launcher test asserting `html.contains("CP-ONLY FRAGMENT CONTENT")` passed on javax but failed on jakarta, where the output was `value:'CP\-ONLY FRAGMENT CONTENT'`. The content *was* rendering — the marker just didn't match. Rule: marker text asserted against rendered ZK HTML must be **hyphen-free** (keep it alphanumeric), or normalize `\-`→`-` before matching. (This is why "APPLIED/INCLUDED/CLASSWEB FRAGMENT CONTENT" markers were fine — no hyphens.)
15. **A user's own `~./` (`ClassWebResource`) page needs the module's resource root on the launcher classpath.** `~./x.zul` resolves from the classpath `/web/x.zul`, but the plugin's `--classpath` was jars-only (`filterLibraryJars` drops directories), so a user resource dir (`src/main/resources/web/…`) was never passed → `Page not found` in preview though it renders under Jetty. Fix: `resolveTarget` also passes resource roots via `filterResourceRoots` (`getSourceRoots(RESOURCE)`) — directories that hold resources, **not** the module output dir (so AC-4(i) class-isolation via the `UiFactory` hook is untouched). Locked by `ClasspathResourceResolutionTest` (resolves iff the resource root is on the render classpath).

## 2026-08-04 — P3 ZUL syntax corpus

17. **A corpus marker must be *load-bearing*: it has to be produced BY the construct under test, not by an unrelated attribute.** In the first P3 pass, `client-onfocus`/`client-shortcut`/`attr-event`/`native-with-zk-child` all asserted a marker (`present=`) that was the widget's own `label`/`value` — so the case proved "the page composes" but nothing about the `w:` listener / long-form `<attribute>` / native passthrough it was named for (deleting the tested attribute left the test green). A Verifier subagent caught all four. Fixes that make a marker load-bearing: put the token INSIDE the mechanism's output (a `w:onFocus="alert('CLIENTFOCUSMARK')"` client-listener body is emitted verbatim into the rendered HTML, so the token appears iff the client attribute was processed); SET the visible property VIA the construct (`<attribute name="label">ATTREVENTLABEL</attribute>`); use a variant with no silent fallback (native `n:fieldset` has no ZUL-component equivalent, so a broken native ns hard-fails on the unknown element instead of silently rendering an ordinary `Div`); or make it a NEGATIVE proof (`zk:if="false"` must HIDE its token — a dropped `zk:` prefix would leak it). Rule: for every "renders" case, ask "if the construct silently did nothing, would this still pass?" — if yes, the marker is decoupled; move it onto the construct's own output. (Same family as lesson #6: HTTP 200 ≠ renders correctly.)

18. **A ZUL corpus is partly discovery — hypothesize→run→lock, but discovery cases still resolved first-run here.** Every one of the 48 P3 cases (incl. `pi-component`, `pi-missing`→GRACEFUL_FAIL, EL `getAttribute`/map/list reads, `annot-namespace` literal-vs-annotation) matched its hypothesized outcome on the FIRST run on both javax+jakarta, so no launcher gaps were found. Keep the discipline anyway: author a hypothesized `Outcome` + marker, run, and only lock what's observed; a defect (crash where Jetty renders) becomes a filed gap, not a silently-relaxed assertion. Data-driven shape that worked: one `@ParameterizedTest` crossing a `List<SyntaxCase>` (group, fixture, outcome, present, absent, phase) with `Variants.both()` via a cartesian `@MethodSource` — 48 cases × 2 variants in one method. Verified deeper by a Playwright live-DOM sample (`SyntaxCorpusBrowserSampleTest`) on 4 representative fixtures.

16. **The preview's "black background" is a `JBCefBrowser` base-paint default, not a page defect.** ZK's layout output sets no background on the root elements (verified against `zk.wcs`: top-level rules are only `html{line-height:normal;…}` and `body{margin:0}`; every `background:#FFFFFF` is scoped to a *widget* body like `.z-window-body`). A normal browser therefore shows its white UA canvas — but `JBCefBrowser` initializes its base paint to the IDE theme color (dark under Darcula), which shows through wherever the page paints nothing, so component-white/everything-else-black. Fix (user-confirmed in runIde 2026-08-04): inject `<style>html{background:#fff}</style>` as the **first** child of `<head>` at the serving boundary (`PreviewHttpServer.withCanvasBackground`) — it reproduces the browser UA default and, being first in the cascade, is overridden by any explicit background a real page/theme sets (faithful). Chosen over plugin-side `JBCefBrowser.setPageBackgroundColor(...)`, which sets an *inline* `document.body.style` (highest priority → would clobber a deliberately dark app), isn't reload-safe, and can't be tested headlessly. Applied at the server, not in the render engines, so `RenderEngine` output stays byte-identical to real ZK. Locked by `PreviewHttpServerTest`.

## 2026-08-04 — P4 Spring Boot jar preview

19. **A ZK EE sample pom needs all THREE ZK repos, or `zkmax` resolves but its transitive `zkex` does not — a partial ZK classpath that dies at runtime, not at resolution.** The P4 `manual-test-springboot/` pom first listed only ZK CE + ZK EE-eval (I dropped the `ZK EE` repo `https://maven.zkoss.org/repo/zk/ee` that `manual-test/` has). Maven resolved `zkmax` but silently failed its transitive `zkex`, so the launcher started, `zkmax`'s `WebAppInit.init` loaded, then blew up: `NoClassDefFoundError: org.zkoss.zkex.ui.comet.CometServerPush$AsyncInfo` (a `zkex` class) → "Failed to bootstrap the ZK mock webapp", exit 1. The pure `DocrootResolverTest` can't catch this (it's dependency-resolution, not path logic). Rules: (a) when creating a new ZK-dependent sample, copy the KNOWN-GOOD repo+dependency block from `manual-test/` verbatim rather than paraphrasing a subset; (b) `NoClassDefFoundError` for a `zkex`/`zkmax` class at `WebAppInit` == a missing/partial ZK EE jar on the classpath, not a plugin bug; (c) after shipping a sample that a manual step depends on, verify it end-to-end (`mvn dependency:tree` for completeness, then drive the real launcher jar against it and `curl` the page) instead of handing back an untested artifact — this is lesson #1 again (production seam), applied to a deliverable I authored.

## 2026-08-04 — ZUL preview code-review must-fixes (C2 dim)

20. **A code reviewer's CONFIRMED finding can have the right symptom but the wrong mechanism — verify the mechanism by running before implementing the "obvious" fix.** Review C2 said `PlaceholderInjector.dim()` "skips dimming when a style is already present" (the `if (style empty)` guard) — plausible from reading, and the styled-components-look-undimmed symptom was real. The obvious fix (append instead of skip) *looks* correct in review but still produced no dim at runtime: instrumenting `dim()` during a real render showed it set the style fine (`after=[color:#9aa0a6;...]`), yet the serialized page never carried it — for styled AND unstyled alike. Real mechanism: **a style set in a `UiLifeCycle.afterComponentAttached` callback does not survive to the serialized page** — ZK overwrites it when it later assigns the component's own static `style` attribute, and otherwise drops it before first-paint serialization. (The text placeholder survives only because ZK never assigns a literal for an `@load` value.) Fix: apply the dim in a **post-composition** sweep from `PreviewComposer.doAfterCompose` (where `injectModels` already runs and demonstrably sticks), appending to the now-final style. Rule: for a visual/property mutation in the preview hooks, mutate post-composition, not at attach time — and prove a fix by rendering, not by re-reading the diff.

21. **Gradle `testLogging.showStandardStreams` stdout is unreliable for debugging — interleaves and drops lines. Dump to a file and Read it.** Chasing C2, `System.out` traces from inside the render came back reordered and incomplete through gradle's capture (a sweep trace for one fixture appeared under another; some lines vanished), sending me down a false "unstyled renders empty" path. Writing each render's HTML to a scratch file and reading it directly gave clean, trustworthy signal. Also: a throwaway diagnostic that renders several fixtures through separate engines in one JVM can still show artifacts (one fixture rendered empty there but rendered fine in the real `ZulSyntaxCorpusTest`); the authoritative check is the real test harness, not the ad-hoc probe.

## 2026-08-04 — ZUL preview code-review should-fixes

22. **A plain-JUnit test that spawns *and destroys* a real process needs an initialized IntelliJ `Application` — so it only passes in a full-suite run, not in isolation.** Running `ManagedPreviewServerTeardownTest` (unmodified, and my new companion test) alone via `--tests` NPE'd at `server.destroy()`: `KillableProcessHandler.destroyProcess()` → `ProgressManager.getInstance()` → `ApplicationManager.getApplication()` returned **null**. The `Application` is a global singleton lazily bootstrapped by the *first* platform-touching test in a run, so these tests are green in the full `:test` suite (some earlier test inits it) but red in isolation. Consequences: (a) don't panic when an isolated `--tests` run of a process-spawning test NPEs on `Application` — re-run it inside the full suite before concluding a regression; (b) prefer designing a fix's unit gate to be **Application-free** — my U2 gate asserts only the *failure* path (`startGuarded` with a throwing supplier → a failed server whose `portFuture` completes exceptionally), which needs no process and no `Application`; I dropped the redundant valid-supplier companion precisely because it dragged in `destroy()`/`Application`. (Also: the CLI-tool sandbox was NOT the cause here — it permits child-process spawning; the failure was purely the missing `Application`.)

## 2026-08-06 — ZUL preview stops updating after the first successful render

23. **Two independent caches produced the identical symptom; fixing the first and stopping cost a round-trip.** "Preview doesn't update after an edit" was caused by (a) ZK's `ResourceCache` 5-second check period on the server, AND (b) JCEF's Chromium HTTP cache on the client. Each alone reproduces the reported sequence exactly, so the first fix passed a real end-to-end HTTP test and the user still saw the bug. Rule: when a symptom is "stale data", enumerate **every** cache on the path (server-side parse cache, HTTP cache, browser cache, IDE VFS) and clear or disprove each *before* declaring the cause — a green test at one layer only exonerates that layer.

24. **Don't dismiss a hypothesis on protocol theory when the artifact is on disk and can be read.** I ruled out browser caching by reasoning about Chromium's `GetFreshnessLifetimes` ("no `Last-Modified` → freshness 0 → always revalidates") and wrote that reasoning into the task doc as "considered and ruled out". It was wrong. `grep -ra "localhost:<port>" ~/Library/Caches/JetBrains/<IDE>/jcef_cache` found the cached entry in seconds, and `strings` on it showed the pre-edit body plus the exact stored headers. Rule: JCEF's cache is inspectable at `~/Library/Caches/JetBrains/<IDE>/jcef_cache/Cache/Cache_Data` — read it instead of predicting it.

25. **Diagnose a "still broken" report against the user's *live* process, read-only, before theorizing.** What settled this: `ps aux | grep zk-preview-launcher` gave the running helper and its args; `lsof -nP -p <pid> -a -iTCP -sTCP:LISTEN` gave its port; `curl` on that port compared against the `.zul` on disk proved the *server* was fresh; the plugin jar under `Library/Application Support/JetBrains/<IDE>/plugins/zkidea/lib/` proved the fix was actually installed (check the class's constant pool with `unzip -p … | strings`, not just the mtime); `idea.log` ruled out exceptions. All read-only, all faster than reasoning. Also: verify a "is the fix present?" probe against a **known-good** artifact first — my first detection loop reported a false "FIX MISSING" on a jar that did contain it.

26. **A live preview resource must be sent `no-store`, and a refresh must revalidate — fix both ends.** Emitting only `Content-Type`/`Content-Length` leaves cacheability to browser heuristics, and `JBCefBrowser.loadURL(sameUrl)` is an ordinary same-URL navigation the cache may answer. Now: `PreviewHttpServer` sends `Cache-Control: no-store, no-cache, must-revalidate` on the rendered page **only** (`/zkau/web/*` assets stay cacheable — one is a 1.6 MB `zk.wpd`), and `ZulPreviewFileEditor` refreshes with `getCefBrowser().reload()`. Either end alone would leave correctness resting on the heuristics that already failed once.

## 2026-08-14 — Issue #66: .zul cannot be opened on IntelliJ 2026.2

27. **A guard that lives *inside* the class it protects cannot protect it.** `ZulPreviewFileEditor` checked `JBCefApp.isSupported()` in its constructor to degrade gracefully, but the class also named `org.cef` types in its own bytecode — so where JCEF is unreachable the JVM failed **verification** at `new ZulPreviewFileEditor(...)` and the guard never ran. Worse, the failure took the whole `.zul` editor with it (the provider declares `HIDE_DEFAULT_EDITOR`), so a preview-only problem became "this file type cannot be opened". Rule: an availability check must sit in a class that links without the thing it checks for, and the optional dependency must be reachable only through a seam whose *declared* type is free of it (a static factory returning the interface loads nothing at verification time; JVMS 4.10.1.2).

28. **`LinkageError` is too coarse for "the class is missing".** `ExceptionInInitializerError` is a `LinkageError` too, and `JBCefApp`'s initializer really can fail on its own (observed against the 2026.2 jars: NPE from `ApplicationManager.getApplication()`). Catching `LinkageError` wholesale would have told users to enable a plugin that was already enabled. Only `NoClassDefFoundError` means "not on this classloader"; everything else is "present but broken" and deserves a different message.

29. **The plugin verifier does NOT model plugin classloader visibility — it cannot catch a missing `<depends>`.** I claimed `runPluginVerifier` would guard this class of bug, then tested it: verifier-cli 1.409 against the real IU-262.8665.258 reported *"Compatible"* both for the fixed artifact and for a control artifact built by stripping only the new `<depends>` line out of the packaged descriptor. It resolves classes against the whole IDE. What it *does* show is the resolved dependency tree — the fixed build gains `(optional) com.intellij.modules.jcef:262.8665.258`, the control does not — which proves the id binds but not that the classes become visible. Rule: for classloader-visibility questions, only a real IDE run is evidence; and the automated guard has to be a test that links the class with the packages hidden.

30. **The test classpath is not the shipped classpath.** These tests could never have caught #66: the Gradle IntelliJ plugin puts every `ideaIC/lib/*.jar` on the test classpath, and `lib/lib-client.jar` — a JetBrains-Client jar the running IDE never loads — happens to contain `org.cef.**`. So a headless test asserting the "JCEF unavailable" fallback linked happily against classes production did not have. Rule: when a test claims to cover "dependency X is absent", check where X actually comes from in the test JVM (`getProtectionDomain().getCodeSource()`) before trusting it.

## 2026-08-20 — P0-2 (`--run-controllers`): three parallel evaluators invented a bug

31. **Parallel subagents that each run `./gradlew` in one shared working tree manufacture failures that look exactly like real ones.** Every evaluator lens in the Planner-Generator-Evaluator workflow ran the launcher suite concurrently against the same `build/` directory. `cleanTest` in one invocation deletes the binary test-report store another is still writing, so the victim build dies with `Could not write XML test results` for up to 28 suites — **zero failing assertions** — and it takes unrelated suites' reports with it, which reads exactly like "the change broke the regression gate". Measured: the same tree is 3/3 green run sequentially, and the failure reproduces on the first attempt with two concurrent runs (`xmlWriteErrors=28`, `assertionFails=0`). Fixed at the source by teaching the workflow's GROUND to copy the tree per gradle run (`rsync --exclude build`) and to never file that signature as a gap.

32. **The agents' run windows are evidence, and they were sitting in the transcript directory the whole time.** `stat` on `agent-*.meta.json` (start) against `agent-*.jsonl` (last write) showed every agent that ran **alone** — planner, both generators — reporting `BUILD SUCCESSFUL`, and every agent that ran in a **concurrent triplet** reporting the corruption. That single table explained the contradiction before I ran anything. Rule: when parallel agents disagree about a flaky measurement, correlate their verdicts with *when they ran* first; it is cheaper than re-running their experiments and it identifies harness artifacts that no amount of re-running will.

33. **Three independent lenses agreeing that something is broken is not evidence that it is broken — they can share a cause.** All three saw the red build. Two concluded "environmental, pre-existing at HEAD"; one built a detailed, plausible, *wrong* causal story (stderr from an unwaited `zk-preview-http-*` handler thread racing Gradle's output boundary) complete with a narrowing experiment and a fix. The mechanism it described is real in the code — `AbstractRenderEngine` really does print on the handler thread, `PreviewHttpServer.stop()` really does not wait — which is what made it convincing. I had a 67-line test helper drafted for it. What killed it was measuring the baseline myself: 3/3 green, so there was nothing to fix. Rule: before implementing a subagent's fix, reproduce the failure it is fixing. A confident mechanism that matches the code can still be a fabrication attached to a real symptom with another cause.

34. **The lenses also contradicted each other on a raw measurement, and that was the tell.** The spec lens reported a clean HEAD copy 4/4 green; the other two reported the same experiment 2/2 red. Both cannot be true, so at least one "verified by execution" claim was noise — which meant the whole attribution question had to be re-measured, not adjudicated from transcripts. Rule: when two agents report opposite results for the *same* command, stop reading their reasoning and run it once yourself.

## 2026-08-23 — P2-6 (viewport flags): two repeats, both self-caught

35. **A compound `cd A && … && git …` sends every later command into A, including the one meant for repo B.** Third occurrence across this engagement, same shape every time: two repos are in play (`agent-skill` for the skill, `zkidea` for the log), the command opens with `cd` into one, and a `git add`/`git status` intended for the other silently targets the first. This time it failed loudly (`pathspec 'tasks/preview-launcher-implementation.md' did not match any files`); the earlier two failed *quietly*, printing one repo's status twice and looking like a clean answer. Rule: **never put a `cd` and a git write for the other repo in one command.** Use `git -C <abs-path>` for every git call when more than one repo is in play, or split the calls. A quiet wrong answer is the dangerous version.

36. **A `criteria`-only run only covers what the criteria happened to ask, and the gap is usually inherited from the brief.** The shipped text claimed "a page whose root region is `vflex`/`hflex` is exactly viewport-tall". True of `vflex`, false of `hflex` — it is a *width*; measured, an `hflex`-only root page holding 1400px of content stitches to 1600x1400, so `--full-page` is right there and `--height` is not. Every generated criterion asked about `vflex`, so the lens passed it. The pairing came from the spec and **I carried it into the brief myself**, so the generator inherited the error rather than inventing it. Second consecutive run where hand verification found a false claim the lens missed (P2-5's raw-argument `zul` was the first). Rule: when writing the brief, check the spec's own phrasing for claims you are about to launder into "measured facts" — and when the lens passes, re-read the shipped text for claims *no criterion mentioned*.

19. **A `--` inside an XML comment makes a `.zul` unparseable — hit twice in one session.** XML
    forbids a double hyphen anywhere inside `<!-- ... -->`, so the em-dash-as-`--` habit used in
    Java comments and Markdown throughout this repo produces a `SAXParseException` ("The string
    "--" is not permitted within comments") and a 500 from the preview. Both times the fixture
    looked fine and the failure surfaced only when the page was actually rendered. Rule: after
    writing or editing any `.zul` comment, run the check below before claiming the fixture works —
    and never trust that a `.zul` is valid because it *reads* valid.
    ```bash
    python3 - <<'PY'
    import pathlib, re
    for f in pathlib.Path(".").rglob("*.zul"):
        for m in re.finditer(r"<!--(.*?)-->", f.read_text(), re.S):
            if "--" in m.group(1):
                print("ILLEGAL '--' in comment:", f)
    PY
    ```
    Corollary that made this expensive: the probe/verification step is what caught it, not review.
    A fixture is not verified until it has been *rendered*, not merely written.
