## U1: ZK render pipeline — what must be served for a browser to display a ZUL page

**Q1 — What DHtmlLayoutServlet emits for a .zul request: CONFIRMED (HTML skeleton + JS that builds widget DOM client-side).** I captured the real initial HTTP response from a live ZK 10.3.0.1 EE server running on localhost:8080. The response is `<!DOCTYPE html><html><head>...</head><body>...</body></html>`. The `<head>` loads ZK JS packages and CSS (see Q2). The `<body>` contains only a loading placeholder (`<div class="z-loading"><div class="z-loading-indicator">...Processing...</div></div>`) plus a bootstrap `<script>`: `zk.themeName='marble';zk.afterLoad(function(){zkmx([0,'dYFV_',{dt:...,cu:...,uu:'/zkau...',rsu:'/zkau...',ru:'/preview.zul'},{},[ ...widget tree... ]])})`. The widget tree is a nested JS/JSON array where each node is `['<widgetClass>','<uuid>',{props},{},[children]]`, e.g. `['zul.wgt.A','dYFVz7',{label:'ZK Framework',href:'https://www.zkoss.org'},{},[]]`. There is NO server-rendered per-component HTML DOM — the browser's ZK Client Engine (`zkmx()`) constructs the widget DOM entirely client-side from this embedded descriptor. Confirmed: no `zAu.send`/ajax call appears in the initial bootstrap; only `zkmx(...)`.
Source: /private/tmp/claude-501/-Users-hawk-Documents-workspace-PLUGIN-zkidea/e4d9d29f-8b69-499d-a543-c5d4330ba5ce/scratchpad/root.html (live server capture)

The server-side flow that produces this: DHtmlLayoutServlet.doGet → process() → WebManager.getDesktop / newPage → creates ExecutionImpl → `wappc.getUiEngine().execNewPage(exec, pagedef, page, out)`. The bootstrap/skeleton is written by HtmlPageRenders (ui/sys): `outZkTags()` writes the JS/CSS `<script>`/`<link>` tags; `outPageContent()` writes `out.write("zkmx(")` (or `"zkx("` for async updates) and iterates roots calling `((ComponentCtrl) root).redraw(out)` to emit the JS widget descriptor `[0,'<pageUuid>',{...},...]`. So generating the response requires ZK's server-side page evaluation engine (interpret ZUL → component tree → redraw to JS). A dumb file server cannot produce it.

Dynamic processing is REQUIRED for most of these — a dumb static extractor is insufficient. (a) `.wpd` files are XML "Web Package Descriptors", not JS. zk.wpd's content is `<package name="zk"><script>window.zk={}</script><function class="org.zkoss.zk.ui.http.Wpds" signature="java.lang.String outLibraryPropertyJavaScript()"/><script src="index.js"/>...</package>` — it embeds server-side Java `<function>` calls whose output is inlined at serve time. WpdExtendlet parses the XML (`new SAXBuilder(...).build(is)`), executes the `<function>` methods, merges/compresses JS, sets content-type `text/javascript;charset=UTF-8`, and caches (`org.zkoss.zk.WPD.cache`). (b) `.css.dsp` files are ZK DSP (Dynamic Server Pages): norm.css.dsp begins `<%@ taglib uri="http://www.zkoss.org/dsp/web/core" prefix="c" %>...<c:if test="${empty c:property('org.zkoss.zul.theme.browserDefault')}">...` — JSP-like conditionals evaluated server-side. (c) `zk.wcs` is XML `<css language="xul/html">` that generates CSS via custom functions per language. So .wpd/.wcs/.dsp require ZK's extendlet processing, not plain file copy.
Source: https://github.com/zkoss/zk/blob/master/zk/src/main/java/org/zkoss/zk/ui/http/WpdExtendlet.java ; jar entries web/js/zk/zk.wpd, web/zul/css/norm.css.dsp, web/zul/css/zk.wcs (verified via `unzip -p`)

Nuance (partial static serving): ZK's "Load JavaScript/CSS from Server Nearby" doc shows a URLEncoder that treats `.wpd`/`.wcs` as static and rewrites them to a resource host — BUT explicitly EXCLUDES `zul.lang.wpd` ("zul.lang.wpd should not be a static resource"), and CSS `.dsp` are also not in the static set. Critically the doc states that "ZK static resource server is an application server which you deploy only official ZK library to" — i.e. even the resource host is a running ZK webapp (a WAR of ZK jars with normal web.xml), not a dumb file server. So: a subset of `.wpd`/`.wcs` can be pre-rendered/cached and served statically, but the merged language descriptor (`zul.lang.wpd`) and `.dsp` CSS need live ZK processing.
Source: /Users/hawk/.zk-doc-mcp/repo/zk_dev_ref/performance_tips/load_javascript_and_css_from_server_nearby.md

**Q3 — Does FIRST rendering require a functioning AU channel?** First paint completes from the initial response + static resources alone; it does NOT require an AU round-trip for a static page. Evidence: the captured bootstrap contains only `zkmx([...])` with the full widget tree embedded (root.html is ~946 KB, the entire component tree with all props inline) and no `zAu.send`/ajax call. `zkmx()` builds the widget DOM synchronously from the embedded descriptor after JS packages load. The AU (async-update) channel is used AFTER load for interactions: per the architecture doc, a client event bubbles to the ZK Client Engine which "decides whether and when to send the event back to the server in an Ajax request" to the ZK Update Engine, which runs listeners and returns AU responses that update widgets. That is a post-load, per-interaction mechanism.
Source: /private/tmp/claude-501/-Users-hawk-Documents-workspace-PLUGIN-zkidea/e4d9d29f-8b69-499d-a543-c5d4330ba5ce/scratchpad/root.html ; /Users/hawk/.zk-doc-mcp/repo/zk_dev_ref/overture/architecture_overview.md

Important caveat on "/zkau is dead": in the default config the SAME servlet (DHtmlUpdateServlet, `/zkau/*`) serves both (i) resources via GET `/zkau/web/...` and (ii) AU commands via POST `/zkau`. If the entire `/zkau` servlet is dead, the JS/CSS `.wpd`/`.wcs`/`.dsp` fail to load and nothing renders at all (blank page stuck on the "Processing..." placeholder). If only the AU POST endpoint is dead while `/zkau/web` GET still serves resources, a static page (labels/links/buttons) still paints fully via `zkmx()`; only subsequent interactions (events, MVVM commands, smartUpdates) and any component that issues a server round-trip on load would break. (I did not empirically simulate a dead-AU-but-live-resources split; this split-behavior conclusion is reasoned from source + the observed no-initial-AU bootstrap.)

**Q4 — Documented stateless / offline / server-side-HTML rendering mode?** ZK has "Stateless Components" (ZK 10) and "Client-side MVVM" (ZK 10), but NEITHER is an offline/static-HTML renderer — both still require a running ZK server and use the identical client-side JS widgets + HTML + CSS. Stateless: components are transient (not kept in HttpSession), client holds authoritative state, actions carry state in each request via a StatelessRichlet; docs state stateless "use the same client-side code (the JavaScript Widgets and associated HTML and CSS code), in addition to a completely different communication and update layer." It reduces server memory, not the need for a server; limitations: no server push, no WebSocket, cannot mix with classic components. Client-MVVM (ClientBindComposer) tracks bindings/commands without creating server-side component instances but is still server-processed. No documented ZK mode renders a ZUL page to finished server-side HTML DOM (no client JS) or renders fully offline without a ZK server. The `stubonly` property only moves per-component state to the client at runtime; it is not offline rendering. ("ZK stateless" therefore does not help a preview that must avoid a running server.)
Source: /Users/hawk/.zk-doc-mcp/repo/zk_dev_ref/stateless_components/stateless_components.md ; /Users/hawk/.zk-doc-mcp/repo/zk_dev_ref/performance_tips/specify_stubonly_for_client_only_components.md

**Cross-cutting fact relevant to the feature.** The ZUL→browser pipeline is fundamentally two-part and both parts need ZK server-side code: (1) evaluate the ZUL into a component tree and `redraw()` it into the `zkmx([...])` JS descriptor (needs zk/zul jars' interpreter + UiEngine), and (2) serve the client resources, most of which (`zul.lang.wpd`, `.css.dsp`, `zk.wcs`) require ZK's WpdExtendlet/DspExtendlet dynamic processing. A "dumb static file server that extracts from jars" is NOT sufficient for either part in the general case; a minimal embedded ZK servlet stack (DHtmlLayoutServlet + DHtmlUpdateServlet/ClassWebResource, or equivalent programmatic use of UiEngine + extendlets) is the load-bearing requirement. The sample project confirms the standard wiring: DHtmlLayoutServlet mapped to `*.zul` with `update-uri=/zkau`, DHtmlUpdateServlet mapped to `/zkau/*`.

## U2: ZATS Mimic feasibility as a servlet-less ZUL renderer

**Summary**: ZATS Mimic loads a ZUL by booting a real, embedded Jetty `WebAppContext` bound to 127.0.0.1 on an ephemeral port inside the same JVM, then makes a genuine `HttpURLConnection` HTTP GET against that local server — so the raw variable it reads (`raw = getReplyString(huc.getInputStream(), ...)`) IS the exact full initial HTTP response HTML a browser would receive; ZATS just doesn't expose that raw string through its public API (it's consumed internally by response handlers to build the component/DOM tree for assertions). It is not on Maven Central; it's distributed only via ZK's own repo (mavensync.zkoss.org), is GPL v2 licensed, and is still actively maintained — the Jakarta/ZK10 track (`org.zkoss.zats:zats-mimic`) released `10.2.1-jakarta` on 2026-04-08, tracking ZK 10.2.1-jakarta exactly. Critically, because the embedded WebAppContext uses `setParentLoaderPriority(true)`, any ViewModel/Composer class ZK's own binder/composer resolution mechanism needs is resolved off the host JVM's classpath — ZATS is purpose-built to instantiate and unit-test those exact classes, and there is no supported switch to suppress that; it directly conflicts with the "never load user-project classes" constraint. No evidence was found of ZATS being used for page snapshot/preview purposes rather than testing.

### Findings

**U2-F1.** ZATS Mimic's connect() flow: it opens a genuine HttpURLConnection GET to an embedded, real Jetty server, reads huc.getInputStream() into a String, and that string is the literal full HTTP response body (HTML) — the same bytes a browser socket would receive.
  - Evidence: EmulatorClient.connect(String zulPath): `HttpURLConnection huc = getConnection(zulPath, "GET"); huc.connect(); ... is = huc.getInputStream(); String raw = getReplyString(is, huc.getContentEncoding());` then `for (LayoutResponseHandler h : handlers) { h.process(desktopAgent, raw); }` and `logger.finest("HTTP response content: " + raw);`
  - Source: https://github.com/zkoss/zats/blob/master/zats-mimic/src/main/java/org/zkoss/zats/mimic/impl/EmulatorClient.java (lines ~130-186)

**U2-F2.** The public Client/DesktopAgent API does not expose that raw HTML string — connect() returns only a DesktopAgent (component-tree handle); the raw HTML is consumed internally by LayoutResponseHandlers and then discarded, not returned to the caller.
  - Evidence: `public DesktopAgent connect(String zulPath) {...}` — return type is DesktopAgent, and `raw` is a local variable never returned or stored on the agent.
  - Source: https://github.com/zkoss/zats/blob/master/zats-mimic/src/main/java/org/zkoss/zats/mimic/impl/EmulatorClient.java; interface at https://github.com/zkoss/zats/blob/master/zats-mimic/src/main/java/org/zkoss/zats/mimic/Client.java

## U3: Prior art - existing ZUL preview/visual-editor implementations

**Summary**: ZK Studio's (Eclipse) Visual Editor is confirmed dead: removed since ZK Studio 2.0.0, source never published on GitHub, and ZK's own staff now recommend a live Jetty/Tomcat server with hot-reload instead of any embedded-preview technology - no documented technical detail on its original rendering mechanism survives. zkfiddle is also dead (last push 2012) but its architecture is documented in its public source: it is NOT a single sandboxed process - it's a thin 'case management' front-end (the datahandler webapp) that registers and proxies to separate, independently-running full ZK webapp instances called 'sandboxes' (one per ZK version/theme), each of which is literally the standard zksandbox.war bundled in ZK's own demo distribution. ZK's own documentation live demos (docs.zkoss.org / zkoss.org) are not per-snippet sandboxes either - they are plain iframe embeds pointing at a single long-running, real zkdemo.war/zksandbox.war Tomcat/Jetty deployment serving static, pre-written ZUL pages. The official ZK VS Code extension has no preview/rendering feature at all (editing assistance only). No other ZUL preview tool (browser-based, VS Code, etc.) with a documented safe-execution/sandbox model was found.

### Agent recommendation (advisory)

For the ZUL Preview v1 plan: no prior-art tool provides a reusable pattern for safely rendering arbitrary ZUL while excluding user classes in-process - both ZK Studio's dead Visual Editor and zkfiddle solved isolation by running a full separate ZK webapp/server (Jetty/Tomcat), not by sandboxing within a single process. This is evidence in favor of a standalone-process/standalone-server rendering core (as already assumed) rather than trying to invent an in-IDE-process emulated servlet; it also confirms zscript/EL execution inside a ZUL page is standard ZK behavior with no special guard rails ZK itself provides against arbitrary code (relevant since the plan already forbids loading user-project classes - ZK framework itself does not enforce that boundary, so the plugin will need its own classpath-scoping mechanism).

## U4: IntelliJ preview-editor + JCEF — current stable pattern for platform range 233.2–261.*

**Summary**: The non-deprecated pattern is: implement a plain `com.intellij.openapi.fileEditor.FileEditorProvider` (optionally `AsyncFileEditorProvider`) registered via the `com.intellij.fileEditorProvider` EP, whose `createEditor()` returns a subclass of the stable `com.intellij.openapi.fileEditor.TextEditorWithPreview` (public since at least the 233 branch, still present on master, just rewritten Java→Kotlin around 2024.3 with source-compatible `@JvmOverloads` constructors). Do NOT depend on `TextEditorWithPreviewProvider` — although JetBrains' 2024.1 migration note names it as the replacement for the now-removed Markdown-plugin-internal `SplitTextEditorProvider`, that class is annotated `@ApiStatus.Internal` on current master. `JBCefApp.isSupported()` gates JCEF availability; the only officially documented unsupported cases are 'alternative JDK without JCEF' and 'incompatible JCEF version' — no official doc names Android Studio or Remote Dev as blanket-unsupported, but a JetBrains-engineer forum reply states there is currently no supported way for a 3rd-party plugin's *composite* editor (TextEditorWithPreview + JCEF) to render client-side in Split Mode/Remote Development; it renders on the backend and streams. No incompatible-changes-list entries were found for TextEditorWithPreview/FileEditorProvider/JBCef between 2024.1 and 2025.3, but the `AsyncFileEditorProvider` experimental async method was renamed/resignatured between 233 (`createEditorBuilder`) and 243+ (`createFileEditor`) — avoid overriding it and stick to the stable `createEditorAsync(): Builder`. IntelliJ Community's own current (2026-dated master) Mermaid-diagram preview provider is a near-exact template for what zkidea needs: gate `accept()` on a filetype/name check + `JBCefApp.isSupported()`, serve rendered content from a `localhost` URL via the built-in HTTP server (`org.jetbrains.ide.HttpRequestHandler` + `BuiltInServerManager`), and push document-change updates into the already-loaded page via `executeCancellableJavaScript()` behind a `Flow.debounce(20ms)` rather than reloading the URL. Finally, `FileEditorProvider.accept(Project, VirtualFile)` takes a `VirtualFile`, not a `FileType`, and zkidea's own codebase already establishes the precedent of gating ZUL-specific logic by `name.endsWith(".zul")` rather than by FileType — necessary because zkidea's plugin.xml maps `.zul` to the shared built-in `XML` FileType, not to a distinct `ZulFileType`.

## U5: Helper-JVM strategy from an IntelliJ plugin — classpath extraction + external process lifecycle

**Summary**: IntelliJ's OrderEnumerator gives a documented API to enumerate a module's or project's runtime classpath (including Maven/Gradle-resolved library jars) via orderEntries(module).recursively().runtimeOnly().classes().getPathsList(), but recursively() is a documented no-op for Maven-imported modules since their transitive deps are already flattened onto the module. ZK version detection is verifiable three ways from the jars themselves (confirmed by unzipping real jars from ~/.m2): jar filename pattern (zk-9.6.4.jar / zul-9.6.4.jar), META-INF/MANIFEST.MF Implementation-Version/Specification-Version, and a ZK-internal metainfo/zk/config.xml with an explicit version-uid plus a org.zkoss.zk.Version.RELEASE compile-time constant. For process lifecycle, GeneralCommandLine + OSProcessHandler (or KillableProcessHandler for two-stage SIGINT/SIGKILL) is the documented and widely-used pattern; JDK selection commonly goes through ProjectRootManager.getInstance(project).getProjectSdk() and JavaSdkType.getVMExecutablePath(); free port allocation has a ready-made util (com.intellij.util.net.NetUtils.findAvailableSocketPort()); and teardown is done by registering the process (or a wrapping Disposable/project service) with Disposer against a project-level service — noting a real, currently-open platform gap around guaranteed termination during full IDE shutdown. Two real open-source plugins (redhat-developer/lsp4ij, flutter/flutter-intellij) show working code for exactly this GeneralCommandLine/OSProcessHandler-based external-process pattern, including a Java-specific command builder (JavaProcessCommandBuilder) analogous to what a ZK preview helper JVM would need.

## Q3 — Pre-transforming the ZUL before ZK parses it

FACT — ZK can parse ZUL from String/Reader/Document (not only a file). `Executions.createComponentsDirectly(String content, String extension, Component parent, Map)` (line 308) plus `Document` and `Reader` overloads. Lower level: `UiFactory.getPageDefinitionDirectly(RequestInfo, String, extension)` / `(RequestInfo, Document, extension)` / `(RequestInfo, Reader, extension)` (UiFactory.java lines 250-286), implemented in `AbstractUiFactory` via `PageDefinitions.getPageDefinitionDirectly` (lines 219-229). So a pre-transformed in-memory ZUL string can be fed directly to the parser.
Source: scratchpad/zk_src/zk101/org/zkoss/zk/ui/Executions.java line 308; scratchpad/zk_src/zk101/org/zkoss/zk/ui/sys/UiFactory.java lines 250-286; scratchpad/zk_src/zk101/org/zkoss/zk/ui/impl/AbstractUiFactory.java lines 219-229

ANALYSIS — ZUL constructs that break under naive text rewriting (sourced behavior):
- `forEach`: repeats a component per element of an EL collection (`compInfo.setForEach(...)`, Parser line 1062). Naively stripping it collapses N rows to 1; leaving it with an unresolved EL collection (null) renders 0 copies (the element disappears).
- `if`/`unless`: EL conditions stored as `ConditionImpl` (Parser line 1061). An unresolved `if="${vm.show}"` evaluates to null -> coerced to false (Type Coercion, Q4) -> element is skipped; `unless` is the inverse. Rewriting these to literals can flip visibility.
- `<zscript>`: evaluated at render by default (Q5); may define variables used by later EL. Stripping it removes those variables (subsequent `${var}` -> empty).
- `<template>` / `@template`: templates are looked up by name at render (e.g. listbox/grid rows, `<template name="model">`). Stripping `@template` or the template definition breaks row/children rendering.

## Q4 — EL referencing an unknown variable (e.g. ${missing.prop})

FACT — Unknown top-level variable resolves to null (no exception) by default. `org.zkoss.zel.impl.parser.AstIdentifier.getValue`: after the resolver chain fails, ZK's zel checks system property `org.zkoss.zel.hideNullTypeException`; when unset or "true" (the default) it calls `ctx.setPropertyResolved(true)` and `return null` instead of throwing (comment: "user can set property as resolved to hide null type exception, default is true"). This is a ZK-specific divergence from stock Apache EL, which would throw PropertyNotFoundException.
Source: scratchpad/zk_src/zel/org/zkoss/zel/impl/parser/AstIdentifier.java lines 108-116

FACT — `${missing.prop}` returns null (not an error). `AstValue.getValue`: `base = children[0].getValue(ctx)` yields null for `missing`; the property loop is `while (base != null && i < propCount)`, so with a null base the loop is skipped and `.prop` is never dereferenced; the final `if (!ctx.isPropertyResolved()) throw PropertyNotFoundException` is satisfied because AstIdentifier already set propertyResolved=true. Result: null. (Contrast: if the base resolves to a real non-null bean but the property is missing, `BeanELResolver` throws PropertyNotFoundException — only fully-unknown chains are null-safe.)
Source: scratchpad/zk_src/zel/org/zkoss/zel/impl/parser/AstValue.java (getValue, while-loop `base != null` guard); scratchpad/zk_src/zk101/org/zkoss/xel/zel/XelELResolver.java lines 100-128

FACT — null coerces to empty string for text/attribute output. ZK Type Coercion table: source type `null` -> String `""` (and `null` is treated the same as an empty string; -> Boolean false, -> Number 0). So `${missing}` / `${missing.prop}` render as an empty string.

## Advisory ranking — highest-fidelity render with zero user-class loading

Rank 1 (recommended, highest fidelity): keep the real ZK Parser + composition, and neutralize the two class-loading paths at ZK level: (a) library property `org.zkoss.bind.defaultComposer.class` -> a preview BindComposer subclass whose `initViewModel` returns a stub VM (keeps binder + @load/@bind/@save/@command rendering as placeholders); (b) custom UiFactory (`ui-factory-class`) overriding `newComposer` to return a no-op composer for `apply="user.X"`. Rely on ZK's default null-safe EL (Q4) so `${...}` and `@load('vm.x')` render empty. This preserves forEach/if/unless/templates/native output faithfully because parsing and composition are unchanged. Keep `org.zkoss.zel.hideNullTypeException` at its default (unset/true).

Rank 2: Rank-1 hooks plus `disable-zscript=true` AND a pre-transform that strips `<zscript>` — only needed if executing zscript at render is a concern; costs fidelity where zscript sets up UI state.

Rank 3 (lowest fidelity): naive XML pre-transform (strip viewModel/apply/forEach, rewrite EL to literals) then parse via `getPageDefinitionDirectly(String)`. Feasible for text but breaks forEach repetition, if/unless visibility, templates, and zscript-defined variables (Q3); use only as a fallback for constructs the ZK-level hooks cannot cover.
