### Key facts the design now rests on (all verified, see RESEARCH.md)

- **F1 (U1)**: The initial ZUL response is an HTML skeleton + `zkmx([...widget tree...])` bootstrap; the browser's ZK client engine builds the DOM. First paint needs **no AU POST round-trip** (static pages), but **does** need `/zkau/web/*` resources, which require ZK's dynamic extendlet processing (`WpdExtendlet` etc.). ⇒ the core must serve resources through ZK code, not by extracting files.
- **F2 (U6)**: Isolation without touching user classes — "Rank 1" recipe **(SUPERSEDED in E1: `BindComposer.initViewModel` is private in zkbind 9.x and 10.x, so the stub-composer half is impossible; implemented instead as a single `UiFactory.newComposer` override that never delegates, blocking both `viewModel=` and `apply=` — plus, in E3 round 3, a `UiFactory.getPageDefinition` override neutralizing annotation-shaped template paths. See §8.)**:
  - library property `org.zkoss.bind.defaultComposer.class` → preview-owned `BindComposer` subclass whose `initViewModel` returns a stub VM (parser reads this at `Parser.java:1051`; binder machinery keeps working, bindings render as placeholders);
  - custom `UiFactory` (`<ui-factory-class>` in zk.xml) overriding `newComposer` → no-op composer for `apply="user.X"`;
  - ZK's EL is null-safe by default (`${missing.prop}` → `""`, no exception).
- **F3 (U6)**: zscript executes at render by default; disabling it makes pages with `<zscript>` fail at parse. v1 policy: leave enabled; a zscript that references missing classes produces a structured failure (AC-6 path).
- **F4 (U4)**: UI = `FileEditorProvider` implemented directly (`TextEditorWithPreviewProvider` doesn't exist in 233) + `TextEditorWithPreview` + `JBCefBrowser`; `accept()` filters by extension (`.zul` shares the XML FileType); gate on `JBCefApp.isSupported()` with a graceful fallback panel; debounce refresh via `MergingUpdateQueue` (plain-Java pattern).
- **F5 (U5)**: Helper JVM: classpath via `OrderEnumerator` (inside read action), ZK version from jar manifests (`Implementation-Version`, stable 6.0→10.4), launch via `GeneralCommandLine`+`KillableProcessHandler`, port via `NetUtils.findAvailableSocketPort()`, lifecycle owned by a `Disposable` project-level service (never parent to Project directly).
- **F6 (U7)**: Isolation is provable cheaply: controlled classpath **(amended by D1/round-2 policy: ALL library jars, never directories — a ZK-only allowlist starves ZK's own deps like slf4j-api)** + narrow parent loader (`ClassLoader.getPlatformClassLoader()`) + cause-chain assertions. The existing spike has a **parent-first fallthrough risk** (`ZkMockRenderer$1` delegates non-`org.zkoss.*` loads parent-first) — in the helper JVM this is mooted (user classes simply absent from the process), but AC-4 still asserts it.

### Architecture (v1 target)

```
IDE process (plugin)                      helper JVM (per project, lazy, Disposable)
┌────────────────────────────┐            ┌──────────────────────────────────────┐
│ ZulPreviewFileEditorProvider│  spawn/    │ zk-preview-launcher.jar              │
│  └ TextEditorWithPreview   │  manage    │  ├ JDK HttpServer on ephemeral port  │
│     └ JBCefBrowser ────────┼──HTTP────▶ │  ├ mock servlet env                  │
│ ZulPreviewServerService    │            │  │  ├ DHtmlLayoutServlet (page)      │
│  (classpath detect, spawn, │            │  │  └ DHtmlUpdateServlet (/zkau/web) │
│   port, teardown)          │            │  ├ isolation hooks (F2)              │
└────────────────────────────┘            │  └ classpath = library jars, no dirs │
                                          └──────────────────────────────────────┘
```

Rendering core = the launcher jar's code: zero IntelliJ imports, callable standalone (`java -jar zk-preview-launcher.jar --classpath ... --webapp ... --port ...`) — satisfies "independently callable".

## 6. Maker/Verifier contract (unchanged from v0)

- **Maker** (user-chosen exec model): implements one phase at a time per this plan. "Done" is a claim, not proof.
- **Verifier** (fresh-context subagent, different model than maker; never shares maker's conversation): judges each gate PASS/FAIL **with evidence** (command output, test results, file paths). Hard conditions only — objective correctness against §5. **Forbidden** to reject for style/naming/narrative/opinion; such notes go to a non-blocking "suggestions" section. Verifier judges, never edits.
- **Loop control**: ≤3 rounds per gate; 2 consecutive rounds without improvement → stop, escalate to user with both rounds' evidence; still FAIL after 3 rounds → stays FAIL, user decides. No "best score wins" softening.
- **Human gates**: commit / push / publish / anything that costs money → explicit user confirmation first, always.
